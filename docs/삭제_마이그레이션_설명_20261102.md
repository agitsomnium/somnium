# 회원 삭제 마이그레이션 — 효과·영향·되돌림 (초안, 미적용)

파일: `supabase/proposed/20261102_member_erasure_DRAFT.sql`(적용), `…_ROLLBACK_DRAFT.sql`(되돌림). **어느 DB에도 적용하지 않았고, 승인 없이 실제 자료를 삭제하지 않았다.** 격리 PostgreSQL 17 시험 PASS(`final-20261102/member-erasure-pg.log`, 삭제 장부·복원 재삭제 시험 포함).

## 왜 필요한가
후원 확인을 요청한 회원은 처리 기록(`audit`)에 행이 생기고, 그 행이 회원 계정을 붙잡아 **회원 삭제가 실패한다**(시험 프로젝트에서 HTTP 500 재현). 이대로 가입을 열면 삭제 요구(시행령 제43조③ 원문: 10일 이내 처리·통지)를 받아도 처리할 수 없는 회원이 생긴다.

## 적용하면 무엇이 바뀌나
| 변경 | 내용 | 기존 자료 영향 |
|---|---|---|
| 구조 | `audit.actor`를 비울 수 있게 하고, 회원이 삭제되면 그 칸만 비워지게(`ON DELETE SET NULL`) 바꿈 | 기존 행 값 변경 **0**. 지금은 아무 행도 달라지지 않음 |
| 함수 추가 | `somnium_erase_member(회원)` — **관리자만** 실행 | 호출 전까지 아무 일도 안 함 |
| 삭제 장부 추가 | 표 `erasure_ledger`(비어 있음) + 운영자 전용 함수 3개(내보내기·가져오기·재적용). 일반 로그인 사용자는 표도 함수도 쓸 수 없음 | 적용만으로 기록·삭제 **0** |
| 현재 원격 시험 DB | 사용자 3(관리자 1·시험 회원 2), 처리 기록 70(전부 관리자 행위), 이용권 0 | 적용만으로 지워지는 것 **없음** |

## 함수를 실제로 호출하면(별도 승인·UI 단추 추가 뒤)
한 회원 한 명에 대해 한 번의 트랜잭션으로:
- 삭제: 프로필(이름·전화·생년월일 등), 후원 확인 요청, 수강 코드 이용권, 코드 시도 기록, 인증 계정·세션.
- 처리 기록: 행은 남기되 그 회원의 UUID·이메일이 들어 있던 `target`을 `erased`로 치환, 행위자 칸은 비움. 삭제 사실 자체는 `member_erased`로 기록(개인정보 없음).
- **거부(오류)**: 본인, 관리자, 후원·이사·코드 승인자로 기록된 계정, **이사 명단에 이메일이 있는 회원**(명단에 이메일이 남아 삭제가 불완전해지므로 기관이 직접 처리). 다른 회원·강의·자료·코드는 건드리지 않는다.
- **삭제 실행 기록(장부):** 호출할 때마다 장부에 한 줄이 남는다. 담기는 것은 ① 회원 UUID와 이메일의 **일방향 해시**(이름·이메일·생년월일·전화·원래 UUID 없음) ② 삭제 시각·실행한 관리자 ③ 지운 건수(프로필·후원 요청·이용권·코드 시도·처리 기록 치환 수). 해시는 «가명»이지 «익명»이 아니다 — 이미 후보 이메일을 가진 사람은 대조해 볼 수 있다.
- 이번에 보강: 이사 명단 회원 거부 + 시험 추가.

## 되돌림
- **함수 호출 전:** 롤백 초안이 구조를 원래대로 복귀(함수 삭제, `actor NOT NULL`, 외래키 원복). 격리 시험: 회원·후원·이용권 수가 적용 전과 같고, 롤백 뒤 다시 적용도 가능.
- **함수 호출 후:** 삭제된 개인정보는 되살릴 수 없다(설계 의도). 롤백 초안은 **장부에 한 줄이라도 있으면 스스로 거부**한다. 이전 판은 `actor`가 빈 행만 봐서, 본인 처리 기록이 없던 회원을 삭제한 뒤에는 거부하지 못했다(빈 행이 생기지 않으므로). 이제 «본인 기록 없는 회원» 시험이 있다 — 그 경우 `actor` 빈 행 0건인데도 롤백이 거부됨을 확인.

## 삭제 전 백업을 복원하면 (격리 시험으로 확인)
- **장부가 없으면 되살아난다:** 삭제 전 백업을 복원하면 계정·프로필·후원 요청·이용권·처리 기록 대상이 모두 돌아온다(시험: 1/1/1/1/3건 부활).
- **절차:** 백업 복원 → 장부 가져오기(백업 «밖»에 보관한 장부 파일) → 재적용. 재적용 뒤 부활분 0건, 다른 회원·관리자는 그대로, 두 번째 적용은 0건 처리(반복해도 안전). 장부 파일에서 이름·이메일·원 UUID가 나오지 않음도 시험.
- **장부는 백업 안에도 들어간다**(백업 도구가 비공개 스키마의 모든 표를 담는다). 단 삭제 «전» 백업에는 그 삭제가 없으므로, 삭제할 때마다 장부를 백업과 **별도로** 내보내 기관 저장소에 두어야 한다(법 제36조③ «복구 또는 재생되지 아니하도록»).
- **이메일을 바꾼 뒤 삭제한 경우:** 장부의 이메일 해시는 삭제 «당시» 이메일이라, 옛 백업에 남은 «예전 이메일»은 해시로 맞지 않는다. 그래서 재적용은 UUID 해시로 복원된 회원을 찾으면 **복원본 자신의 이메일을 읽어** 처리 기록의 해당 이메일·UUID 흔적을 지운 뒤 계정을 삭제한다. 이 이메일은 장부에 저장하지 않는다. 시험: 백업 → 이메일 변경 → 삭제 → 옛 백업 복원 → 재적용 후 전체 데이터 덤프에서 예전·새 이메일·이름·전화·생년월일·UUID 흔적 0건(이 보강을 빼면 예전 이메일 1건이 남아 시험이 실패함을 확인).
- 복원본이 관리자이거나 이사 명단에 이메일이 있으면 재적용은 멈추고 사람이 확인한다. 같은 이메일로 **새로 가입한 다른 UUID 계정**은 지우지 않는다(UUID로만 일치).
- **장부 도구 `supabase/ops/erasure_ledger.py`:** `export`(DB → 파일, 다른 폴더 저장본 복사, 두 파일 재읽기, DB 재조회 대조), `verify`(저장 파일 대 현재 DB). 대조는 ID만이 아니라 같은 ID의 이메일 해시·삭제 시각·삭제 건수까지 전체 항목 단위이며, `apply`도 가져온 뒤 같은 기준으로 확인하고 DB에 이미 내용이 다른 같은 ID가 있으면 멈춘다, `apply`(복원 후 가져오기·재적용·남은 회원 0 확인·두 번째 실행 0). 어느 단계든 어긋나면 `FAILED … 완료로 보고하지 말 것`과 종료코드 1이다. 마지막 줄이 `OK`로 시작할 때만 완료다. 파일에 `@`·UUID 모양·형식 밖 칸이 있으면 거부한다. 시험으로 확인한 실패 경로: 해시 편집, 항목 삭제 후 지문 재계산, 같은 ID의 건수·이메일 해시·삭제 시각을 바꾸고 지문만 재계산, 내용이 다른 같은 ID가 이미 있는 DB에 적용, 해시 칸의 이메일, 파일 없음, 손상 파일 적용, 저장 폴더 = 출력 폴더, 쓸 수 없는 저장 위치, 내보낸 뒤 추가 삭제로 낡은 파일.
- 한계: 이것은 격리 DB의 논리 복원이다. 실제 Auth 서비스 복원은 시험하지 않았다.

## 적용 전 순서(최종 운영 전환안에 포함)
0) 장부 내보내기·보관 절차 담당 지정 1) 새 백업 + 복호화·무결성 점검 통과 2) 적용 승인 3) 적용 4) 시험 계정으로만 호출 시험(실회원 아님) 5) 관리자 화면 «회원 삭제» 단추 추가·시험(현재 단추 없음, 호출은 RPC뿐).
